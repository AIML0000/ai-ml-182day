The ML lifecycle is the SRE lifecycle in a lab coat

The JD's very first responsibility lists the whole ML lifecycle: data ingestion → feature engineering → training → evaluation → deployment → monitoring → retraining → rollback. Yesterday you saw the one-line mapping. Today, go one level deeper — because in the interview you'll be asked to walk this lifecycle, and your edge is being able to say "that stage is X in the systems I already operate."

The takeaway Six of these eight stages are things you already do; only training/tracking and evaluation are genuinely new craft. That's the whole reason a senior title is realistic — you're adding modeling skill on top of an operations spine most ML-only candidates lack.

Why a real repo, and real remote state

Two habits separate a "did a course" candidate from a "ships to production" one, and you'll bake both in today:

1 · A structured repo. Exploration (notebooks) is kept separate from reusable code (src/) and from infrastructure (infra/). Each of your ten portfolio projects gets its own folder. This is what a reviewer opens, and it signals engineering maturity instantly.

2 · Remote Terraform state. Day 1 kept state in a local file — fine for one person, one machine. Real teams put state in a shared, locked, encrypted backend so changes are collaborative, durable, and never sitting in Git. Moving it there is exactly the "controlled configuration management" the JD asks for, and it's a satisfying, concrete lab.

LAB 2

Stand up a remote state backend

Terraform

Terraform needs somewhere to store state before Terraform manages it — a classic bootstrap. Create a dedicated Storage Account + blob container with the Azure CLI (kept separate from your app infra), so it survives even a full destroy.

backend-bootstrap.sh
RG=tfstate-rg
LOC=centralindia
SA=tfstate$RANDOM$RANDOM          # must be globally unique, lowercase

az group create -n $RG -l $LOC
az storage account create -n $SA -g $RG -l $LOC \
  --sku Standard_LRS --encryption-services blob --min-tls-version TLS1_2
az storage container create -n tfstate --account-name $SA

echo "Storage account: $SA"      # note this name for the backend block
Why the CLI, not Terraform, for this

Chicken-and-egg: you can't store the backend's own state in the backend before it exists. Bootstrapping the state container out-of-band (CLI) is the standard, pragmatic pattern. Some teams manage it with a tiny separate Terraform config using local state — either is defensible; the CLI is simpler and you'll rarely touch it again.

Why a separate resource group

tfstate-rg is deliberately not mllab-rg. Your app foundation gets created and destroyed constantly during learning; the state store must outlive those cycles. Never let Terraform manage the thing that holds its own state.

Verify
shell
az storage account show -n $SA -g $RG --query name -o tsv
az storage container list --account-name $SA -o table   # tfstate listed
LAB 3

Migrate Terraform state to the backend

Terraform

Point your Day-1 infra/foundation/ config at the remote backend and migrate the existing local state into it. Add the backend block, then re-init.

infra/foundation/backend.tf
terraform {
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstateXXXXXXXX"   # the $SA from Lab 2
    container_name       = "tfstate"
    key                  = "foundation/terraform.tfstate"
  }
}
migrate
cd infra/foundation
terraform init -migrate-state     # prompts to copy local state to Azure -> yes
terraform plan                    # should show: No changes.
Expected
output
Initializing the backend...
Do you want to copy existing state to the new backend?
  Enter a value: yes

Successfully configured the backend "azurerm"!
...
No changes. Your infrastructure matches the configuration.

"No changes" after migration is the whole point: same resources, state just lives in Azure now. Your local terraform.tfstate becomes a stale backup — it's already git-ignored.

The key is a namespace

key = "foundation/terraform.tfstate" is the blob path inside the container. Give each project its own key (projects/02-classifier/terraform.tfstate) so many stacks share one backend without colliding.

State locking — a free interview point

The azurerm backend locks state using a blob lease automatically. If a second apply runs concurrently, it's blocked until the first releases the lease — no separate lock table needed (unlike AWS's DynamoDB). That's how remote state prevents two people corrupting infra at once.

If it fails on auth

The backend reaches the storage account using your az login session. If you get a 403, you either lack rights to list the account keys, or you're using AAD auth without the Storage Blob Data Contributor role. Fix: confirm the right subscription is active, or assign that role to yourself on the storage account.

Interview and scenario questions for today's material. Answer before expanding.

Walk me through the end-to-end ML lifecycle.interview
Data is ingested and turned into features; models are trained with every run's params and metrics tracked; candidates are evaluated and the winner is registered and version-controlled; it's promoted through Dev→Test→Prod and deployed behind an endpoint on a cluster; in production it's monitored for latency, health, data drift, and prediction quality; when drift or new data warrants it, a retraining pipeline runs, gated by evaluation before promotion; and if a new version underperforms, you roll back to the last good one. The operational half — deploy, monitor, retrain, rollback — is standard release engineering; the modeling half — train, evaluate — is the ML-specific craft.
Why move Terraform state to a remote backend instead of keeping it local?system design
Four reasons. Collaboration: a shared backend is the single source of truth, so teammates aren't each holding a divergent state file. Locking: the azurerm backend takes a blob lease so two applies can't corrupt state concurrently. Durability: replicated cloud storage beats one laptop's disk. Security: state can contain secrets in plaintext, so it belongs in access-controlled, encrypted storage — never in Git. It's the "controlled configuration management" the JD asks for, made real.
How would you structure an ML project repository, and why?practical
Separate concerns by folder: infra/ for Terraform, notebooks/ for throwaway exploration, src/ for code that's been promoted to reusable, tested modules, projects/ for each deliverable, and docs/ for design notes and diagrams. The key discipline is that notebooks are for discovery and don't ship — once logic is worth keeping, it moves to src/ where it can be imported, tested, and packaged. A reviewer can then tell at a glance what's exploratory and what's production-bound, which signals maturity.
How does model "retraining" relate to the CI/CD you already run?translation
Retraining is a CD pipeline with an ML-specific trigger and gate. Instead of a code commit kicking off build→test→deploy, the trigger is a schedule, a drift alarm, or new labeled data; instead of unit tests as the gate, an evaluation metric (e.g. accuracy ≥ current prod) must pass before the new model is promoted. The plumbing — automated, gated, auditable, with rollback — is identical to what I run today; only the artifact (a model) and the gate (a metric) differ.
What does state locking protect against, and how does the azurerm backend do it?concept
It protects against two concurrent operations mutating the same state and corrupting it — e.g. two engineers running apply at once, ending with a state file that matches neither reality. The azurerm backend acquires a lease on the state blob at the start of a write operation; a second operation can't acquire the lease and waits or fails fast, so writes serialize. It's automatic — no separate lock table like AWS's DynamoDB. If a process dies mid-apply and leaves a stale lease, you can force-unlock, carefully.
Error-fix: terraform init -migrate-state fails with a 403 reaching the backend storage. Diagnose it.error-fix
The backend can't authenticate to the storage account. Check, in order: 1) Is the right subscription active? az account show — the storage account must live there. 2) Do the storage_account_name / container_name in the backend block exactly match what Lab 2 created (typo in the random name is common)? 3) Auth mode — by default the backend fetches the account key via your session, which needs rights to list keys; if the account enforces AAD auth, you instead need the Storage Blob Data Contributor role assigned to your identity on that account. 4) A storage firewall/network rule can block your IP — check the account's networking settings. Assign the role or fix the name/subscription, then re-run.
