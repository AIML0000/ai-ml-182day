Four containers, four jobs

Python gives you four built-in containers. They differ on three axes — ordered?, mutable?, duplicates allowed? — and that's what decides which one fits. Get this right and your ML code is both correct and fast; get it wrong and you'll write an O(n²) loop where an O(n) one would do.

TypeOrderedMutableDuplicatesReach for it when…
listyesyesyesan ordered, growable sequence — rows of a dataset, a batch of samples
tupleyesnoyesa fixed record that shouldn't change — a coordinate, a return value, a dict key
dictyes*yeskeys uniquekey→value lookups — feature maps, config, counting, caching
setnoyesnouniqueness & fast membership — dedupe, label sets, "seen already?"

*dict preserves insertion order since Python 3.7 — but you rely on it for iteration order, not for sorting.

The performance point (this is the SRE angle)

The single most important thing on this page: checking membership in a list is O(n) — Python scans every element — while a set or dict does it in O(1) via hashing. If you're filtering a million log lines against a set of known-bad hosts, host in bad_hosts is instant when bad_hosts is a set and painfully slow when it's a list. Same code, 1000× difference at scale.

why it matters
known_bad = ["h1", "h2", ..., "h9999"]        # list  -> `x in known_bad` scans up to 10k items
known_bad = {"h1", "h2", ..., "h9999"}        # set   -> `x in known_bad` is one hash lookup

Mutable vs immutable — and why it decides keys

A dict key or a set element must be hashable, which in practice means immutable: str, int, tuple, frozenset qualify; list, dict, set do not. The reason is simple — a hash table finds items by a value computed from their contents, so if the contents could change, the item would get "lost" in the table. That's why a tuple can be a dict key (e.g. (region, service)) but a list cannot.

ML framing A dataset is a list of records; each record is often a dict of feature-name → value; the set of distinct class labels is a set; a fixed (row, col) index or a model's (precision, recall) result is a tuple. You'll use all four before you ever import scikit-learn.

LAB 1

Lists — a batch of pod restart counts

Python

You have restart counts for pods in a deployment. Print how many pods there are, the total restarts, the max, and the list sorted highest-first. Then append a new pod's count and re-check the total.

starter
restarts = [0, 2, 0, 7, 1, 0, 3]
# TODO: count, total, max, sorted desc; then append 5 and re-total
solution
restarts = [0, 2, 0, 7, 1, 0, 3]

print(len(restarts))            # 7
print(sum(restarts))            # 13
print(max(restarts))            # 7
print(sorted(restarts, reverse=True))   # [7, 3, 2, 1, 0, 0, 0]

restarts.append(5)
print(sum(restarts))            # 18
Notes

sorted() returns a new list and leaves the original untouched; restarts.sort() would sort in place and return None. append() mutates the list in place — lists are mutable, which is exactly why they're the right choice for a growing collection.

LAB 2

Dicts — host → CPU%, and counting log levels

Python

Build a dict of host → cpu%. Look up one host, update another, and iterate to print any host above 80%. Then, given a list of log levels, count how many times each level appears — without knowing the levels in advance.

starter
cpu = {"web-01": 42, "web-02": 91, "db-01": 66}
levels = ["INFO", "ERROR", "INFO", "WARN", "ERROR", "INFO"]
# TODO: lookup web-01; set web-03=75; print hosts > 80; count levels
solution
cpu = {"web-01": 42, "web-02": 91, "db-01": 66}

print(cpu["web-01"])            # 42
cpu["web-03"] = 75             # add / update a key

for host, pct in cpu.items():
    if pct > 80:
        print(host, pct)        # web-02 91

levels = ["INFO", "ERROR", "INFO", "WARN", "ERROR", "INFO"]
counts = {}
for lvl in levels:
    counts[lvl] = counts.get(lvl, 0) + 1
print(counts)   # {'INFO': 3, 'ERROR': 2, 'WARN': 1}
Notes

cpu["missing"] raises KeyError; use cpu.get("missing") (returns None) or cpu.get("missing", 0) for a default. The counts.get(lvl, 0) + 1 idiom is the canonical "count without pre-initialising keys" pattern — you'll meet its shortcut, collections.Counter, on Day 15.

LAB 3

Sets — dedupe services & compare two regions

Python

From a noisy list of service names (with duplicates), get the unique set. Then, given the services seen in two regions, find which run in both, and which run in eastus but not centralindia.

starter
seen = ["auth", "api", "auth", "cache", "api", "auth"]
eastus = {"auth", "api", "cache", "search"}
india  = {"auth", "api", "billing"}
# TODO: unique services; in both regions; in eastus only
solution
seen = ["auth", "api", "auth", "cache", "api", "auth"]
print(set(seen))               # {'auth', 'api', 'cache'}  (order may vary)

eastus = {"auth", "api", "cache", "search"}
india  = {"auth", "api", "billing"}

print(eastus & india)          # {'auth', 'api'}      intersection = in both
print(eastus - india)          # {'cache', 'search'}  difference = eastus only
print(eastus | india)          # union = everything, deduped
Notes

set(seen) dedupes in one call — the most common real use of sets. The operators read like the algebra: & intersection, - difference, | union, ^ symmetric difference. Sets are unordered, so never rely on their print order.

LAB 4

Tuples — composite keys & why a list can't be one

Python

You want latency keyed by both region and service. Use a (region, service) tuple as the dict key. Then try to use a list as a key and observe what happens — and explain why.

starter
latency = {}
# TODO: latency[("eastus","api")] = 120 ; look it up
# TODO: try latency[["eastus","api"]] = 120 and note the error
solution
latency = {}
latency[("eastus", "api")] = 120
latency[("india", "api")]  = 95

print(latency[("eastus", "api")])      # 120

# a list as a key fails:
latency[["eastus", "api"]] = 120
# TypeError: unhashable type: 'list'
Why

A dict finds a key by hashing it. A tuple is immutable, so its hash is stable and it's a valid key. A list is mutable — its contents (and therefore its hash) could change after insertion, which would strand the entry — so Python forbids it: unhashable type: 'list'. Composite keys like (region, service) are a clean, idiomatic pattern you'll see constantly.

Mini-project — aggregate metrics from log lines

Save to src/

Given raw log lines "host cpu", compute the average CPU per host and the set of unique hosts — using all four containers. Save it as src/day03_containers.py, run it, and commit.

src/day03_containers.py
lines = [
    "web-01 42", "web-02 91", "web-01 55",
    "db-01 66", "web-02 88", "db-01 70",
]

# TODO:
#  1. parse each line into a (host, cpu) tuple  -> list of tuples
#  2. group cpu readings per host               -> dict of host -> list
#  3. print average cpu per host
#  4. print the set of unique hosts
src/day03_containers.py
lines = [
    "web-01 42", "web-02 91", "web-01 55",
    "db-01 66", "web-02 88", "db-01 70",
]

# 1. parse -> list of (host, cpu) tuples
records = []
for line in lines:
    host, cpu = line.split()          # split on whitespace -> 2 strings
    records.append((host, int(cpu)))  # tuple: fixed 2-field record

# 2. group cpu readings per host -> dict of host -> list of ints
by_host = {}
for host, cpu in records:
    by_host.setdefault(host, []).append(cpu)

# 3. average per host
for host, readings in by_host.items():
    avg = sum(readings) / len(readings)
    print(f"{host}: avg cpu {avg:.1f} over {len(readings)} samples")

# 4. unique hosts
print("hosts:", set(by_host))
run it
python src/day03_containers.py
expected output

web-02: avg cpu 89.5 over 2 samples
db-01: avg cpu 68.0 over 2 samples
hosts: {'web-01', 'web-02', 'db-01'}
Why this is the whole day in one script

list holds the ordered records; each record is a tuple (fixed shape, safe to unpack); dict groups readings by host with the setdefault(host, []).append(...) idiom; set gives unique hosts for free via set(by_host) (iterating a dict yields its keys). This "parse → group → aggregate" shape is exactly what you'll do to a real dataset before any modeling.

Scenario and interview-style questions. Think through your answer before expanding.

You're filtering millions of records against a "known bad hosts" collection. Does it matter if that collection is a list or a set?performance
Enormously. Each membership test host in known_bad is O(n) on a list (Python scans it) and O(1) on a set (one hash lookup). Filtering m records against n bad hosts is O(m·n) with a list and O(m) with a set. At millions of records that's the difference between seconds and effectively hung. Rule of thumb: if you built a collection just to test membership against it, make it a set.
Why can a tuple be a dictionary key but a list can't?concept
Dict keys must be hashable, and hashability requires the value to be immutable. A dict stores a key by a hash computed from its contents; if the contents could change after insertion, the stored hash would no longer match and the entry would be unreachable. A tuple is immutable, so its hash is stable — valid key. A list is mutable, so Python refuses it with TypeError: unhashable type: 'list'. This is why composite keys are written as tuples, e.g. metrics[(region, service)].
A function needs to return a fixed set of values — say precision and recall. List or tuple?design
Tuple. The result has a fixed shape and fixed meaning (position 0 is precision, position 1 is recall), and it shouldn't be mutated by the caller — that's exactly what a tuple signals. It also unpacks cleanly: precision, recall = evaluate(model). Reach for a list when the number of elements is variable and the caller may grow or shrink it; reach for a tuple for a fixed, heterogeneous record. (Later you'll meet NamedTuple/dataclass for when you want named fields too.)
How would you deduplicate a list while preserving the original order?practical
A plain set(items) dedupes but loses order. To keep first-seen order, use list(dict.fromkeys(items)) — dicts preserve insertion order and enforce unique keys, so it does both in one expression. The explicit form is a loop with a seen set: add to the result only when x not in seen, then seen.add(x). Both are O(n); the dict.fromkeys one-liner is the idiomatic choice.
What's the danger in writing def collect(x, acc=[]) as a function signature?gotcha
The classic mutable default argument bug. The default [] is created once, when the function is defined, and shared across every call that doesn't pass acc. So acc accumulates across calls and results bleed together. The fix is the standard idiom: default to None and create the list inside — def collect(x, acc=None): acc = [] if acc is None else acc. The same trap applies to {} and set() defaults. It's a favourite interview question precisely because it catches people who don't know when default values are evaluated.
You need to count occurrences of each item in a large stream. What's the clean way?practical
A dict with the counts[x] = counts.get(x, 0) + 1 idiom works and shows you understand the mechanics. In real code you'd reach for collections.Counter(stream), which does exactly this and adds helpers like .most_common(5). Both are O(n) and O(k) space for k distinct items. Mentioning you'd start with the dict idiom and know Counter as the batteries-included version is a good "I know the fundamentals and the tools" answer.
