Read the JD carefully and you'll see it's split roughly in half: one half is modeling (ML, deep learning, GenAI, agents) and the other half is operating models in production reliably, securely, and at scale — CI/CD, Docker, Kubernetes/AKS, Helm, monitoring, RBAC, Key Vault, auditable infra changes. That second half is your day job as an SRE lead. Today is about seeing that clearly and building on it.

LAB 1

Bootstrap the portfolio repo

Core

Create the repo you'll grow across the track: an isolated Python virtual environment, the core ML libraries, a sane .gitignore (never commit state files or secrets), and a first commit.

bootstrap.sh
mkdir ai-ml-182day
cd ai-ml-182day

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
pip install numpy pandas scikit-learn jupyter
pip freeze > requirements.txt

git init
printf '.venv/\n__pycache__/\n*.pyc\n.terraform/\n*.tfstate*\nterraform.tfvars\n.env\n' > .gitignore
git add .
git commit -m "chore: bootstrap ai-ml portfolio"
Why each line matters

venv isolates dependencies so Day 40's PyTorch can't break Day 10's pandas. requirements.txt makes the environment reproducible — the same idea as pinning image versions. The .gitignore is the important one: *.tfstate* and terraform.tfvars and .env keep Terraform state (which can contain secrets in plaintext) and credentials out of Git. Committing state to a public repo is a classic, costly leak.

Verify
shell
git log --oneline     # one commit shown
git status --ignored  # .venv/ etc. listed as ignored, not staged
LAB 2

Provision the Azure foundation with Terraform

Terraform

Declare a Resource Group + Storage Account + Key Vault as code. This is the shared foundation the Azure ML labs (Days 121–140) will build on. Create the four files below in an infra/ folder inside your repo, then run the workflow.

infra/versions.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
    random  = { source = "hashicorp/random",  version = "~> 3.6" }
  }
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id   # required in azurerm v4
}
infra/variables.tf
variable "subscription_id" {
  type        = string
  description = "Your Azure subscription ID"
}
variable "location" {
  type    = string
  default = "centralindia"
}
variable "prefix" {
  type    = string
  default = "mllab"
}
infra/main.tf
resource "random_string" "suffix" {
  length  = 6
  special = false
  upper   = false
}

data "azurerm_client_config" "current" {}

resource "azurerm_resource_group" "ml" {
  name     = "${var.prefix}-rg"
  location = var.location
  tags     = { purpose = "ai-ml-182day", owner = "thrilochana" }
}

resource "azurerm_storage_account" "ml" {
  name                     = "${var.prefix}sa${random_string.suffix.result}"
  resource_group_name      = azurerm_resource_group.ml.name
  location                 = azurerm_resource_group.ml.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  tags                     = azurerm_resource_group.ml.tags
}

resource "azurerm_key_vault" "ml" {
  name                       = "${var.prefix}-kv-${random_string.suffix.result}"
  resource_group_name        = azurerm_resource_group.ml.name
  location                   = azurerm_resource_group.ml.location
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  soft_delete_retention_days = 7
  purge_protection_enabled   = false
  rbac_authorization_enabled  = true
}

# Grant *yourself* rights to write secrets (used in Lab 3)
resource "azurerm_role_assignment" "kv_secrets" {
  scope                = azurerm_key_vault.ml.id
  role_definition_name = "Key Vault Secrets Officer"
  principal_id         = data.azurerm_client_config.current.object_id
}
infra/outputs.tf
output "resource_group"  { value = azurerm_resource_group.ml.name }
output "storage_account" { value = azurerm_storage_account.ml.name }
output "key_vault_uri"   { value = azurerm_key_vault.ml.vault_uri }
run the workflow
cd infra
az login                                     # if not already
export TF_VAR_subscription_id=$(az account show --query id -o tsv)

terraform init      # downloads providers
terraform fmt       # auto-format (habit)
terraform validate  # static checks
terraform plan      # READ THIS before applying
terraform apply     # type: yes
What plan should say

Plan: 5 to add, 0 to change, 0 to destroy. — the RG, storage account, key vault, role assignment, and the random suffix. If it says anything to change or destroy on a first run, stop and read why.

What apply should end with
output
Apply complete! Resources: 5 added, 0 changed, 0 destroyed.

Outputs:
key_vault_uri   = "https://mllab-kv-a1b2c3.vault.azure.net/"
resource_group  = "mllab-rg"
storage_account = "mllabsaa1b2c3"
Verify out-of-band (trust, but confirm)
shell
az group show -n mllab-rg -o table
terraform state list   # the 5 objects Terraform now manages
Design notes (interview-ready)

Random suffix: storage account and Key Vault names are globally unique across all of Azure, so a random 6-char suffix avoids "name already taken" failures. RBAC auth on the vault (rbac_authorization_enabled = true) uses Azure roles instead of legacy access policies — the modern, auditable pattern the JD implies. Tags give you cost attribution and ownership, exactly like tagging infra in prod.

Common failures & fixes
ErrorFix
subscription_id is requiredYou skipped the export. Run export TF_VAR_subscription_id=$(az account show --query id -o tsv)
Role assignment: AuthorizationFailedYour account isn't Owner/User Access Administrator on the subscription. On a personal PAYG sub you usually are — re-check az account show points to the right one.
Vault name in "soft-deleted" stateYou destroyed & recreated. Either change prefix, or purge: az keyvault purge --name <old-name>
LAB 3

Store a secret in Key Vault (as code)

Terraform

The JD calls out "Azure Key Vault and secure ML practices." Add a secret to your vault declaratively — the same mechanism you'll later use for an Azure OpenAI key. Append this to main.tf, then apply again.

infra/main.tf (append)
resource "azurerm_key_vault_secret" "demo" {
  name         = "demo-api-key"
  value        = "placeholder-rotate-me"
  key_vault_id = azurerm_key_vault.ml.id
  depends_on   = [azurerm_role_assignment.kv_secrets]
}
Why depends_on

Writing a secret needs the "Secrets Officer" role to already exist. Terraform can't infer that ordering from the attributes alone, so you declare it explicitly. Without it, the secret write can race the role assignment and fail with a 403.

Verify
shell
az keyvault secret show --vault-name <your-kv-name> --name demo-api-key --query value -o tsv
# -> placeholder-rotate-me
The real-world caveat

That secret value now sits in plaintext inside your Terraform state file — which is exactly why *.tfstate* is in your .gitignore. In production you'd use a remote backend (Azure Storage) with encryption and access control, and inject secrets at runtime rather than hardcoding them. Good instinct to flag in an interview. (You'll set up that remote backend on Day 2.)

Cost & naming notes

  • Resource Group: free. Storage (LRS, idle): a few paise/day. Key Vault (standard): free tier of operations covers all learning use.
  • Storage account name: 3–24 chars, lowercase letters + digits only, globally unique.
  • Key Vault name: 3–24 chars, alphanumeric + hyphens, globally unique, can't start with a digit.
  • Region: centralindia keeps latency low from Hyderabad; some AI services are region-limited — you'll pick per-service later.

Scenario and interview-style questions — the kind you'll actually face for this role. Think through your answer before expanding.

You've been an SRE, not an ML engineer. Why should we consider you for a Senior AI/ML Engineer role?positioning
Lead with the shape of the role, not an apology. A senior AI/ML role that emphasizes MLOps, scalability, reliability, security, and governance is 50–60% production engineering — and that's my day job: I run systems at scale, own CI/CD, Kubernetes, observability, and secrets management. I've closed the modeling gap deliberately — here are the projects (classification, anomaly detection, a RAG app, an agent). So you get someone who won't just train a model in a notebook but can operate it reliably in production from day one, which is where most ML projects actually fail. Be honest about the newer areas; pair every gap with evidence you've built toward it.
The JD wants "reviewable and auditable infrastructure changes." Design that for an ML platform.system design
Everything as code in Terraform (or Bicep), stored in Git. Changes flow through pull requests with required reviewers; CI runs terraform plan and posts the diff on the PR so reviewers see exactly what will change; merge triggers apply. State lives in a remote backend (Azure Storage) with locking and encryption. Add policy-as-code (OPA/Sentinel) to block, say, public storage or untagged resources. K8s workloads are templated with Helm for reproducible, reviewable deploys. Every resource is tagged for ownership/cost, and Azure Activity Logs give the audit trail. This is the same governance you already apply to app infra — models are just another artifact in the pipeline.
How does your observability background translate to ML model monitoring?translation
The four golden signals map almost directly: latency → inference/response latency; traffic → request volume; errors → failed or timed-out predictions; saturation → GPU/CPU/memory on the serving fleet. ML then adds signals classic apps don't have: data drift (are inputs still shaped like training data?), model drift / quality (is accuracy holding against ground truth?), and for GenAI, groundedness and hallucination rate. I'd wire these into the same dashboards and alerting discipline I use now, and express targets as SLOs with error budgets — e.g., "p95 prediction latency < 200ms" and "weekly accuracy ≥ threshold."
Explain the difference between data drift and model drift, and how you'd detect each.concept
Data drift is a shift in the input distribution — the features coming in no longer look like training data (new user behavior, a changed upstream source). Detect it by comparing live feature distributions to a training baseline with statistical tests (KS test, Population Stability Index). It needs no labels, so you catch it early. Model (concept) drift is when the relationship between inputs and the target changes, so the model's learned mapping is stale and accuracy drops even if inputs look normal. Detect it by tracking live performance against actual outcomes once labels arrive — which is delayed, so data-drift alarms are your leading indicator and performance metrics are the confirming one.
Scenario: terraform apply fails with a 401 / "could not acquire access token." Walk me through debugging it.debugging
Work from auth outward. 1) Am I logged in and pointed at the right subscription? az account show — confirm the ID matches TF_VAR_subscription_id. 2) Is the token stale? Force a refresh with az account get-access-token or re-run az login. 3) Are conflicting ARM_* env vars (e.g. leftover service-principal creds) overriding my CLI login? env | grep ARM_ and unset if so. 4) On azurerm v4, is subscription_id actually set in the provider or via the env var? 5) Rarely, clock skew on the machine invalidates the token — check system time. The discipline is the same as any prod auth issue: identify the identity, its scope, and the token's validity, in that order.
Error-fix: re-running apply after a destroy throws "A resource with this ID already exists — must be imported." What happened and how do you resolve it?error-fix
Terraform's state and reality have diverged: the resource exists in Azure but isn't in Terraform's state — commonly a soft-deleted Key Vault whose globally-unique name is still reserved, or a resource created out-of-band. Three resolutions: (a) bring it under management with terraform import <address> <azure-id>; (b) if it's a soft-deleted vault you don't want, purge it (az keyvault purge --name <name>) then re-apply; or (c) change the name (bump the prefix or random suffix) so Terraform creates a fresh one. The root lesson: state is Terraform's source of truth, and drift between state and reality is what you're reconciling.
